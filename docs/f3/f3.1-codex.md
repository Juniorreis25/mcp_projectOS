## Configuração suportada verificada

A documentação oficial do Codex CLI confirma servidores MCP HTTP via `url`, autenticação por `bearer_token_env_var` e cabeçalhos adicionais por `env_http_headers`:

- [Docs MCP — configuração do Codex](https://developers.openai.com/learn/docs-mcp)
- [Config reference](https://developers.openai.com/ja-JP/docs/config-file/config-reference)

A tentativa foi feita sem persistir configuração global, usando configuração inline equivalente a:

```toml
[mcp_servers.projectos_f3]
url = "https://projectos-7l9g4cwf9-juniors-projects-21c34634.vercel.app/mcp"
bearer_token_env_var = "PROJECTOS_MCP_TOKEN"
env_http_headers = { "x-vercel-protection-bypass" = "VERCEL_AUTOMATION_BYPASS_SECRET" }
enabled_tools = ["projectos.list_skills", "projectos.get_skill"]
```

Os dois valores são placeholders de nomes de variáveis; nenhum segredo foi colocado no arquivo. `bearer_token_env_var` fornece o Bearer do ProjectOS e `env_http_headers` fornece o cabeçalho HTTP do bypass Vercel a partir do ambiente. `http_headers_helper` não é uma alternativa equivalente para este caso: a referência do Codex limita esse helper a servidores HTTP conectados localmente.

O valor de nenhum segredo foi impresso, registrado, versionado ou incluído nas evidências. A variável `PROJECTOS_MCP_TOKEN` não estava presente nos ambientes processo/usuário/máquina verificados. A variável `VERCEL_AUTOMATION_BYPASS_SECRET` também não estava presente nesses ambientes. O conector Vercel só foi consultado com `decrypt=false`; não há autorização nesta rodada para gerar, alterar ou revogar o bypass.

O mecanismo oficial da Vercel é o Protection Bypass for Automation, usando `x-vercel-protection-bypass`. O segredo pode liberar múltiplos deployments do projeto até ser revogado; por isso deve ser tratado como credencial sensível, com armazenamento seguro, uso mínimo e rotação/revogação controlada. Não foi usado parâmetro de query string.

Conclusão: a conexão autenticada não foi tentada. O próximo teste só pode ocorrer após o Orquestrador autorizar a injeção segura dos dois segredos no ambiente do Codex, sem commit, log ou exposição no chat.

### Logs sanitizados do Codex

O Codex registrou falha de inicialização do servidor remoto durante `initialize`, com resposta HTTP `401` da proteção Vercel. Nonces, tokens e cabeçalhos não foram preservados. A mesma causa foi reproduzida no preview atual com um POST MCP sanitizado sem credenciais: a resposta foi da camada Vercel, não do handler ProjectOS.

Uma segunda tentativa com `bearer_token_env_var` falhou localmente porque `PROJECTOS_MCP_TOKEN` não estava definido. Isso confirma que a configuração segura é reconhecida pelo cliente, mas não fornece a credencial necessária nem atravessa a proteção SSO da Vercel.

## Separação das evidências

- **Diretamente pelo Codex:** tentativa de configuração MCP HTTP, handshake `initialize`, observação do `401` da Vercel e confirmação de que nenhuma tool ficou disponível.
- **Fora do Codex:** health check, metadados do deployment e validações HTTP anteriores do preview. Esses resultados não são apresentados como teste de interoperabilidade Codex.

## Auditoria GitHub–Vercel

- O projeto `projectos-mcp` está ligado ao repositório `Juniorreis25/mcp_projectOS`, com criação de deployments Git habilitada.
- A configuração retornou `productionBranch: main`; pushes/merges nessa branch geraram deployments `target=production` automaticamente. Isso explica os deployments de produção observados após a integração e atualização do Plano-Mestre.
- Domínios de produção configurados: `projectos-mcp.vercel.app`, `projectos-mcp-juniors-projects-21c34634.vercel.app` e `projectos-mcp-git-main-juniors-projects-21c34634.vercel.app`.
- SSO Vercel está ativo para deployments não customizados. A proteção por senha está desativada e trusted IPs não estão habilitados.
- A auditoria de variáveis retornou `PROJECTOS_MCP_TOKEN` apenas em `preview`; não há configuração equivalente visível para `production`. A rota do ProjectOS exige esse segredo para autorizar Bearer, portanto a autenticação de aplicação em produção não pode ser considerada operacional sem uma variável de produção. Nenhuma requisição foi feita a produção.

Antes de novos merges que devam gerar produção, o Orquestrador deve decidir se a configuração GitHub–Vercel continuará promovendo `main` automaticamente e como será provisionado o segredo de runtime de produção. Nenhuma configuração foi alterada nesta rodada.

## Riscos e próximo passo

O bloqueio precisa ser resolvido por uma alternativa suportada, sem tornar o preview público e sem desabilitar a autenticação do ProjectOS. Opções a avaliar pelo Orquestrador:

1. autorizar o uso mínimo de um segredo existente de Protection Bypass for Automation e injetá-lo no ambiente do Codex como `VERCEL_AUTOMATION_BYPASS_SECRET`, junto do `PROJECTOS_MCP_TOKEN`;
2. usar um endpoint de preview acessível ao Codex com proteção compatível e Bearer do ProjectOS mantido;
3. disponibilizar um ambiente de teste MCP dedicado, não produtivo, dentro do limite de segurança aprovado.

Não é recomendado usar token em URL, desabilitar SSO, remover o Bearer do ProjectOS ou testar o deployment `target=production`.

Também foi observado que o projeto Vercel está conectado à branch `main` e gerou automaticamente deployments com `target=production` após pushes em `main`. Isso não foi acionado manualmente nesta F3.1, mas é uma pendência de governança do pipeline antes de novos merges.

Sem os dois pré-requisitos de segredo, F3.1 permanece bloqueada; F3.2 não deve iniciar.
