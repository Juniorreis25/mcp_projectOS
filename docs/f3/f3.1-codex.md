## Configuração suportada verificada

A documentação oficial do Codex CLI confirma servidores MCP HTTP via `url`, autenticação por `bearer_token_env_var` e cabeçalhos adicionais por `env_http_headers`:

- [Docs MCP — configuração do Codex](https://developers.openai.com/learn/docs-mcp)
- [Config reference](https://developers.openai.com/ja-JP/docs/config-file/config-reference)

A tentativa foi feita sem persistir configuração global, usando configuração inline equivalente a:

```toml
[mcp_servers.projectos_f3]
url = "https://projectos-7l9g4cwf9-juniors-projects-21c34634.vercel.app/mcp"
bearer_token_env_var = "PROJECTOS_MCP_TOKEN"
env_http_headers = { "x-vercel-protection-bypass" = "VERCEL_AUTOMATION_BYPASS_SECRET" }
enabled_tools = ["projectos.list_skills", "projectos.get_skill"]
```

Os dois valores são placeholders de nomes de variáveis; nenhum segredo foi colocado no arquivo. `bearer_token_env_var` fornece o Bearer do ProjectOS e `env_http_headers` fornece o cabeçalho HTTP do bypass Vercel a partir do ambiente. `http_headers_helper` não é uma alternativa equivalente para este caso: a referência do Codex limita esse helper a servidores HTTP conectados localmente.

O valor de nenhum segredo foi impresso, registrado, versionado ou incluído nas evidências. A variável `PROJECTOS_MCP_TOKEN` não estava presente nos ambientes processo/usuário/máquina verificados. A variável `VERCEL_AUTOMATION_BYPASS_SECRET` também não estava presente nesses ambientes. O conector Vercel só foi consultado com `decrypt=false`; não há autorização nesta rodada para gerar, alterar ou revogar o bypass.

O mecanismo oficial da Vercel é o Protection Bypass for Automation, usando `x-vercel-protection-bypass`. O segredo pode liberar múltiplos deployments do projeto até ser revogado; por isso deve ser tratado como credencial sensível, com armazenamento seguro, uso mínimo e rotação/revogação controlada. Não foi usado parâmetro de query string.

## Disponibilidade do bypass

O projeto `projectos-mcp` está no plano Hobby. A documentação oficial da Vercel declara o Protection Bypass for Automation disponível em todos os planos; portanto o recurso é compatível com o plano do projeto. A configuração atual mantém SSO habilitado (`all_except_custom_domains`), sem alteração nesta rodada.

A presença de um segredo já criado não foi confirmada: o conector usado para a auditoria oferece mutação para gerar/alterar/revogar bypass, mas não foi autorizado a executar essas operações nem a descriptografar valores. O procedimento depende de uma pessoa com permissão de membro da equipe ou Project Administrator, conforme a documentação oficial.

Também não será usado `vercel curl` nesta preparação. Embora ele possa acrescentar o cabeçalho automaticamente, a CLI pode recuperar ou criar um bypass; isso seria uma mutação potencial e, além disso, não testaria a interoperabilidade real do Codex.

## Procedimento seguro para Windows/PowerShell

O provisionamento deve ser feito pelo responsável autorizado, fora do chat e sem colocar os valores em arquivos. A sessão deve ser nova e dedicada. O script abaixo pede os dois valores como `SecureString`, coloca-os somente no ambiente do processo PowerShell e não os imprime:

```powershell
function Set-ProjectOSF31SessionSecrets {
  $projectSecure = Read-Host 'ProjectOS MCP token' -AsSecureString
  $bypassSecure = Read-Host 'Vercel automation bypass secret' -AsSecureString
  $projectPtr = $null
  $bypassPtr = $null

  try {
    $projectPtr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($projectSecure)
    $bypassPtr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($bypassSecure)
    $env:PROJECTOS_MCP_TOKEN = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($projectPtr)
    $env:VERCEL_AUTOMATION_BYPASS_SECRET = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($bypassPtr)
  }
  finally {
    if ($projectPtr) { [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($projectPtr) }
    if ($bypassPtr) { [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($bypassPtr) }
    Remove-Variable projectSecure, bypassSecure, projectPtr, bypassPtr -ErrorAction SilentlyContinue
  }
}

Set-ProjectOSF31SessionSecrets
```

Não usar `setx`, variáveis de usuário/máquina, `.env`, `.env.local`, `config.toml` com valores, clipboard ou parâmetros de linha de comando. A configuração do Codex deve conter somente nomes de variáveis:

```toml
[mcp_servers.projectos_f3]
url = "https://<preview>/mcp"
bearer_token_env_var = "PROJECTOS_MCP_TOKEN"
env_http_headers = { "x-vercel-protection-bypass" = "VERCEL_AUTOMATION_BYPASS_SECRET" }
enabled_tools = ["projectos.list_skills", "projectos.get_skill"]
```

## Verificação sem revelar valores

Antes de qualquer conexão, verificar somente presença no ambiente do processo:

```powershell
@('PROJECTOS_MCP_TOKEN', 'VERCEL_AUTOMATION_BYPASS_SECRET') |
  ForEach-Object {
    $value = [Environment]::GetEnvironmentVariable($_, 'Process')
    [pscustomobject]@{ Name = $_; Present = -not [string]::IsNullOrEmpty($value) }
  }
```

O resultado esperado é `Present = True` para os dois nomes. Não usar `Write-Host $value`, `Get-ChildItem Env:`, logs de ambiente ou qualquer comando que liste valores.

O Codex Desktop não herda alterações feitas em uma janela PowerShell já aberta. Para a primeira validação, o Codex CLI deve ser iniciado na mesma sessão PowerShell depois da verificação. Um processo Desktop já aberto deve ser encerrado e reiniciado por um mecanismo que realmente receba as variáveis; se isso não puder ser comprovado sem persistir credenciais, a validação pelo Desktop permanece bloqueada. Não configurar as variáveis como User ou Machine.

## Limpeza e revogação

Após encerrar o processo Codex e todos os clientes que receberam as variáveis:

```powershell
Remove-Item Env:PROJECTOS_MCP_TOKEN -ErrorAction SilentlyContinue
Remove-Item Env:VERCEL_AUTOMATION_BYPASS_SECRET -ErrorAction SilentlyContinue
```

Repetir a verificação de presença e confirmar `Present = False`. Fechar a janela PowerShell dedicada. Se o segredo tiver sido exposto, reutilizado fora do escopo ou se a política exigir revogação, um responsável com permissão deve revogá-lo no Vercel em **Settings → Deployment Protection → Protection Bypass for Automation** e criar outro somente após aprovação. A documentação informa que a regeneração/seleção de um novo segredo pode exigir novo deployment para que o valor atualizado seja aplicado.

Nenhuma limpeza de segredo ou revogação foi executada nesta rodada porque nenhum segredo foi provisionado.

## Alternativa se o bypass não for compatível

Não desabilitar SSO nem remover o Bearer. As alternativas seguras são:

1. usar o token OIDC de desenvolvimento de curta duração da Vercel no cabeçalho `x-vercel-trusted-oidc-idp-token`, somente se o cliente conseguir obtê-lo e enviá-lo por `env_http_headers`, com a regra Trusted Sources aprovada;
2. usar um ambiente MCP dedicado, não produtivo, com proteção compatível e o Bearer do ProjectOS;
3. usar `vercel curl` apenas para smoke HTTP externo, nunca como substituto do teste real do Codex.

Nenhuma dessas alternativas foi configurada ou testada nesta etapa.

- **Codex instalado:** presente, `codex-cli 0.162.0-alpha.2`.

## Auditoria GitHub–Vercel

- O projeto `projectos-mcp` está ligado ao repositório `Juniorreis25/mcp_projectOS`, com criação de deployments Git habilitada.
- A configuração retornou `productionBranch: main`; pushes/merges nessa branch geraram deployments `target=production` automaticamente. Isso explica os deployments de produção observados após a integração e atualização do Plano-Mestre.
- Domínios de produção configurados: `projectos-mcp.vercel.app`, `projectos-mcp-juniors-projects-21c34634.vercel.app` e `projectos-mcp-git-main-juniors-projects-21c34634.vercel.app`.
- SSO Vercel está ativo para deployments não customizados. A proteção por senha está desativada e trusted IPs não estão habilitados.
- A auditoria de variáveis retornou `PROJECTOS_MCP_TOKEN` apenas em `preview`; não há configuração equivalente visível para `production`. A rota do ProjectOS exige esse segredo para autorizar Bearer, portanto a autenticação de aplicação em produção não pode ser considerada operacional sem uma variável de produção. Nenhuma requisição foi feita a produção.

Antes de novos merges que devam gerar produção, o Orquestrador deve decidir se a configuração GitHub–Vercel continuará promovendo `main` automaticamente e como será provisionado o segredo de runtime de produção. Nenhuma configuração foi alterada nesta rodada.

Recomendação de governança: proteger `main` no GitHub, impedir pushes diretos, exigir os checks F1/F2 e promover para produção somente por uma etapa explícita de release. Enquanto isso não estiver decidido, as próximas fases devem trabalhar em branches de preview e não integrar em `main`. Não alterar a configuração Vercel automaticamente durante esta F3.1.

## Riscos e próximo passo

O bloqueio precisa ser resolvido por uma alternativa suportada, sem tornar o preview público e sem desabilitar a autenticação do ProjectOS. Opções a avaliar pelo Orquestrador:

1. autorizar o uso mínimo de um segredo existente de Protection Bypass for Automation e injetá-lo no ambiente do Codex como `VERCEL_AUTOMATION_BYPASS_SECRET`, junto do `PROJECTOS_MCP_TOKEN`;
2. usar um endpoint de preview acessível ao Codex com proteção compatível e Bearer do ProjectOS mantido;
3. disponibilizar um ambiente de teste MCP dedicado, não produtivo, dentro do limite de segurança aprovado.

Não é recomendado usar token em URL, desabilitar SSO, remover o Bearer do ProjectOS ou testar o deployment `target=production`.

Também foi observado que o projeto Vercel está conectado à branch `main` e gerou automaticamente deployments com `target=production` após pushes em `main`. Isso não foi acionado manualmente nesta F3.1, mas é uma pendência de governança do pipeline antes de novos merges.

Sem os dois pré-requisitos de segredo, F3.1 permanece bloqueada; F3.2 não deve iniciar.
